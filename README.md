# English Lab

一个面向中国本科生的英语阅读与词汇学习应用。核心闭环：**读文章 → 点不会的词 → 看语境释义 → 自动进生词本 → 后续文章自动标记 → 间隔复习 → 阅读理解测试 → 数据记录**。

界面按 Apple 原生应用的规范做：浅色/深色主题、玻璃浮层、衬线正文排版、克制的动效。所有学习数据存在本机，刷新、关闭浏览器都不丢。

---

## 快速开始

```bash
cd english-lab
npm install
npm run dev          # 开发模式，http://127.0.0.1:5173
```

生产构建与本地预览：

```bash
npm run build        # tsc -b && vite build → dist/
npm run preview      # http://127.0.0.1:4173
```

内容与测试：

```bash
npm run validate:content   # 校验 44 篇文章的结构、逐字引用、词数区间
npm test                   # 单元测试（vitest，7 个文件 228 项）

# 端到端验收：playwright 已在 devDependencies 里，但浏览器二进制不随 npm install 下载
npx playwright install chromium
npm run preview            # 另开一个终端
npm run test:e2e           # 64 项检查 + 截图
```

部署：`dist/` 是纯静态产物，可直接放到任意静态托管（Vercel / Netlify / Nginx / 对象存储）。路由用 hash（`#/library`），不需要服务端 rewrite 规则。产物约 22MB（17 个 JS 文件 + 2,641 个按需加载的词典 JSON 分片），部署时注意托管平台的单站文件数上限。

## 技术选型与理由

| 选择 | 理由 |
|---|---|
| **Vite + React 18 + TypeScript** | 无服务端渲染需求（单用户本地应用），Vite 冷启动与构建都在 2 秒内；React 的组件化对 10 个页面 + 阅读器浮层这类交互密集的界面更省事；TS strict 用来兜住数据模型 |
| **手写 CSS + 设计 Token** | 没有用 Tailwind 或组件库。Apple 风格的关键是排版细节（字号阶梯、行高、留白、玻璃层次），原子类反而让这些细节散落难控。`src/styles/tokens.css` 用 CSS 变量集中管理颜色/间距/圆角/阴影/动效 |
| **localStorage + 版本化迁移** | 单用户、数据量小（44 篇文章 + 数百生词 ≈ 100KB 量级），localStorage 足够且零运维。`src/lib/storage.ts` 有 `CURRENT_VERSION` 与 `migrate()`，字段缺失、类型错误、版本超前都能容错读取 |
| **hash 路由（自写 60 行）** | 静态部署不需要服务端 rewrite；不引入 react-router 省掉一个依赖 |
| **词典本地优先** | 核心词典（217 词条 + 24 条固定搭配）人工校订，覆盖高频词与易混词；其余交给内置的 ECDICT 离线库（2,641 个分片 / 19.87 万词头 / 15MB 产物），按前缀分层 fetch、离线可用、零调用成本。代价是 `dist/` 约 22MB、2,600+ 个文件，但 JS 只有 17 个、首屏约 578KB，词典分片首屏不加载。在线接口只作为未收录词的可选兜底 |
| **不引入图表库** | 统计页只需要柱状图 + 热力图，flex/grid 就够，省掉 100KB+ 依赖 |
| **不引入状态管理库** | `useSyncExternalStore` + 一个 60 行的 store 就够，避免 Redux/Zustand 的样板代码 |

依赖总数：运行时仅 `react` / `react-dom`；开发依赖 `vite` / `typescript` / `@vitejs/plugin-react` / `vitest` / `playwright` / `eslint`（含 typescript-eslint、react-hooks 插件）与 TS 类型包。`playwright` 只在跑端到端验收时用，浏览器二进制需要手动装一次。

## 词典层：四级来源，宁缺勿假

`src/lib/dict.ts` 的 `lookupWord()` 按优先级取数据，并且**明确告诉用户释义来自哪一级**：

1. **核心词典**（`src/data/lexicon.ts`）—— 人工校订，含音标、多义项、搭配、同族词、词义联系、近义词辨析。覆盖 217 个高价值词（四级/考研高频、多义词、易混词）+ 24 条固定搭配。
2. **文章标注**（每篇文章的 `glossary`）—— 由内容作者为本文写的语境释义，共 1,649 条。
3. **离线词典 ECDICT**（`public/dict/` + `src/lib/offline-dictionary.ts`）—— 内置英汉词库，MIT 许可（上游 [skywind3000/ECDICT](https://github.com/skywind3000/ECDICT)）：**2,641 个 JSON 分片、共 15MB**，覆盖 198,720 个带中文释义的词头与 48,702 个词形索引，附带音标与多义项。数据以静态文件放在 `public/dict/`，**不参与 JS 打包**，运行时用 `fetch` 按需读取。这一级是通用词典释义，不是语境翻译，也没有逐条人工校审。
4. **在线词典**（默认关闭）—— `dictionaryapi.dev`（Wiktionary，CC BY-SA）。用户在设置里手动开启后才会联网，6 秒超时，结果缓存 30 天。

第四级之所以默认关闭，是因为前三级的覆盖已经足够日常阅读；在线接口只是未收录词的可选兜底。

### 分片策略：为什么是 2,641 片而不是 740 片

词库按单词前缀**分层分片**，单片上限 60KB：先按前两个字母分（`ab.json`、`co.json`…），超过 60KB 的组再按第三个字母拆（`co.json` → `con.json` → `cons.json`…），`manifest.json` 记录全部分片名。查询时从最长前缀往短探测，取第一个命中的分片。

早期版本按前两个字母一刀切，热门前缀（`co` / `re` / `de` / `in`）的分片达到 500–770KB，在低带宽下点一个词要等 20 秒以上，用户会以为「点了没释义」。分层拆分后最大分片 59KB，配合进入阅读器时的清单预热，首次点词通常 1–2 秒出结果。

这套分片由 `scripts/build-dict-shards.mjs` 生成（源数据在 `src/data/ecdict/`）：只保留「有音标的词条」或「文章正文出现过的词」，剔除大量生僻专有名词，词条数从 399,200 降到 198,720，体积从 26MB 降到 15MB。

离线库的代价要说清楚：`dist/` 约 22MB，其中词典分片占 15MB（2,641 个 JSON 文件），JS 只有 17 个文件。首屏加载约 578KB（`index` 22KB + `articles` 391KB + `ui` 158KB），词典分片首屏完全不加载。托管平台的**单站文件数上限**要按 2,600+ 这个量级评估——这是比体积更需要注意的约束。

语境释义的可信度会显式标注：

- `本文标注` —— 内容作者为该词在本文的含义写的释义
- `固定搭配` —— 句中命中词典里的搭配（如 `maintain a healthy lifestyle`）
- `按词性推测` —— 只依据词性匹配，可靠性低，界面上明确写「请结合上下文」

词典查不到时：**照常收藏该词**，释义标为「待补充」，绝不编造音标或释义。音标缺失就显示「音标未收录」。

发音用浏览器原生 `SpeechSynthesis`（英式/美式可选），不依赖任何音频文件或第三方 TTS。

## 复习算法（可解释）

`src/lib/srs.ts` 是 SM-2 的变体，无随机数、可单测：

| 评分 | 间隔变化 | 难度因子 |
|---|---|---|
| 忘了 | 立即重来（10 分钟后） | −0.20 |
| 勉强 | `max(1, 间隔 × 1.2)` | −0.15 |
| 记得 | `max(1, 间隔 × 难度因子)` | 不变 |
| 很熟 | `max(2, 间隔 × 难度因子 × 1.3)` | +0.15 |

难度因子夹在 1.3–2.8，间隔上限 365 天。**掌握门槛**：连续答对 ≥ 4 次且当前间隔 ≥ 21 天，或用户手动标记。收藏 ≠ 掌握，统计里分开算。

## 统计口径

两个容易混的指标，产品里明确分开：

- **实际阅读词数** = Σ 各文章「已读句子的词数」（按滚动位置推进，句子粒度）
- **完成文章总词数** = Σ 已标记读完的文章的总词数

其余指标的口径写在 `src/lib/stats.ts` 的 `METRIC_DEFINITIONS` 里，统计页底部直接展示给用户看。

## 已知限制

诚实列出来，不掩饰：

1. **单用户本地部署**。数据在浏览器 localStorage，换设备/清缓存会丢，需要手动导出 JSON 备份。多用户登录与云同步未实现，数据模型与迁移层已为此预留（见 `docs/DATA-MODEL.md`）。
2. **没有后端**。所以也没有服务端输入校验、鉴权、限流——当前架构下这些没有意义。一旦接入多用户，必须先补服务端。
3. **在线词典在国内大概率不可用**。`dictionaryapi.dev` 本机实测 SSL 连接失败。核心词典、文章标注与 ECDICT 离线库覆盖了绝大多数点击场景，四级全未命中的词会明确提示「释义待补充」。
4. **语境消歧是启发式的**，不是 NLP 级词义消歧。依据是「本文标注 > 固定搭配命中 > 词性匹配」，界面会标注可信度。ECDICT 给的是通用词典释义，不含语境判断。
5. **音标覆盖不完整**。核心词典 217 个词带人工校订音标；ECDICT 分片里上游有音标的词也能显示；文章 glossary 一律不提供音标（避免内容作者编造），两级都没有时显示「音标未收录」。
6. **文章是原创内容，不是真题**。44 篇覆盖 11 个主题、4 个难度，但难度分级是产品内部教学分层，不等于 CEFR 或任何官方等级，也不宣称用户达到某一水平。
7. **阅读进度是句子粒度**，不是字符级。恢复位置会落在句首。
8. **朗读依赖系统语音包**。Windows/macOS 自带英语语音可用；无语音包的设备会提示不可用，不会静默失败。
9. **移动端是底部导航 + 全屏面板**，没有把桌面三栏硬压成三栏——这是有意为之。
10. **构建产物文件数偏多**。离线词库让 `dist/` 达到约 22MB、2,600+ 个文件（2,641 个词典 JSON 分片 + 17 个 JS）。JS 体积很小、首屏约 578KB，但托管平台的**单站文件数上限**、CDN 回源次数要按这个量级评估；仓库体积也因此增加约 41MB（源数据 26MB + 生成产物 15MB）。
